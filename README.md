# terraform-aws-aurora-postgresql

A Terraform module for one Amazon Aurora PostgreSQL cluster: Aurora Serverless v2 by
default (provisioned instance classes allowed), its instances, a DB subnet group, a
dedicated security group and an enhanced-monitoring role. It is secure by default:
storage encrypted, deletion protection on, a final snapshot on destroy, IAM database
authentication on, the master password generated by RDS and kept in Secrets Manager
(never in Terraform state), the PostgreSQL log exported to CloudWatch Logs,
Performance Insights on, no public access and no egress.

Use it when a service needs a PostgreSQL database in private subnets you already
have. You do not need to know anything about the project it came from.

It deliberately does **not** manage:

- **What is inside the database.** Schemas, migrations, roles and grants belong to
  the application or a migration tool, not to the infrastructure module.
- **Who may connect.** Clients are admitted by security group, with
  `allowed_security_group_ids` or with your own rules on `security_group_id`.
  Database users that sign in with IAM need an IAM policy you attach to them.
- **Parameter groups, AWS Backup plans, RDS Proxy and global databases.** See
  [design decisions](docs/explanation/design-decisions.md) for why.
- **The network and provider configuration.** Pass in a VPC and private subnets;
  there is no `provider` or `backend` block.

## Usage

```hcl
module "aurora" {
  source = "git::https://github.com/EG2development/terraform-aws-aurora-postgresql.git?ref=v1.0.0" # x-release-please-version

  name           = "payments-prod"
  engine_version = "18.4"
  vpc_id         = module.vpc.vpc_id
  subnet_ids     = module.vpc.private_subnet_ids

  allowed_security_group_ids = { app = aws_security_group.app.id }
}
```

Pin `?ref=`
to a release tag (inside the organisation) or the release's full commit SHA (outside
it), never to a branch. Run `terraform init` after changing `source`.

## Defaults and security decisions

| Decision | Default | Why | How to change it |
| --- | --- | --- | --- |
| Master password | Generated and rotated by RDS in Secrets Manager | The password never appears in configuration, plans or state | `manage_master_user_password = false` with `master_password` (stored in state) |
| Storage encryption | On, AWS managed key for RDS | Data, snapshots and backups are encrypted at rest | `kms_key_arn` for a customer managed key (also used for Performance Insights); encryption cannot be turned off |
| Deletion | Deletion protection on; final snapshot `<name>-final` on destroy | A mistaken destroy, in Terraform or anywhere else, loses nothing | `deletion_protection = false`, `skip_final_snapshot = true` |
| Backups | 7 days of point-in-time recovery; snapshots copy the cluster's tags | Recovers from bad writes, not only lost hardware | `backup_retention_period`, `preferred_backup_window` |
| Network access | No ingress, no egress, never publicly accessible | Only clients you name can connect, and the database cannot reach out | `allowed_security_group_ids`, or rules on `security_group_id`; public access is not configurable |
| Authentication | IAM database authentication on | Applications can sign in with short-lived tokens instead of stored passwords | `iam_database_authentication_enabled = false` |
| Logs and metrics | PostgreSQL log to CloudWatch Logs; enhanced monitoring every 60 s; Performance Insights on | Evidence after an incident and data for tuning | `enabled_cloudwatch_logs_exports`, `monitoring_interval`, `performance_insights_enabled` |
| Monitoring role | Trusts only `monitoring.rds.amazonaws.com` acting for DB instances in this account and Region; holds only `AmazonRDSEnhancedMonitoringRole` | Least privilege and confused-deputy protection | `monitoring_interval = 0` removes it |
| Engine upgrades | Minor versions automatic; major versions refused | Security fixes arrive; a breaking upgrade never happens by accident | `auto_minor_version_upgrade`, `allow_major_version_upgrade` |
| Engine version | No default | A major version is a decision | `engine_version` (required) |

## Security scanning

Checkov runs on every pull request via
[Static Analysis](.github/workflows/workflow.yml). Three AWS checks are skipped in
[`configs/checkov.yml`](configs/checkov.yml):

| Check | Why it is skipped |
| --- | --- |
| `CKV2_AWS_5` "Security Groups are attached to another resource" | Fails only in `examples/complete`: its application security group stands in for the group of the caller's application, which the example does not create. The module's own group is always attached to the cluster, and `tests/defaults.tftest.hcl` asserts it |
| `CKV2_AWS_8` "RDS clusters has backup plan of AWS Backup" | AWS Backup plans are set per account or organisation, not per database module. The cluster keeps 7 days of automated backups and a final snapshot by default |
| `CKV2_AWS_27` "Postgres RDS as aws_rds_cluster has Query Logging enabled" | Query logging is set in a cluster parameter group, which this module leaves out (see [design decisions](docs/explanation/design-decisions.md)). It also writes SQL text, including literal values, to the logs: a privacy decision for the owner of the data. The PostgreSQL server log is exported by default |

The customer managed key checks `CKV_AWS_327` (storage) and `CKV_AWS_354`
(Performance Insights) pass because both arguments are wired to `kms_key_arn`.
Checkov cannot see that the default is null: callers who set no key get the AWS
managed key for RDS, a deliberate default (see the table above).

## Upgrading

Read [`CHANGELOG.md`](CHANGELOG.md) for every version between yours and the new one,
change `?ref=`, run `terraform init`, and review the plan. A minor or patch release
plans no changes unless you opt into something new. Changing `name`,
`database_name`, `master_username`, `kms_key_arn` or `db_subnet_group_name` replaces
the cluster with a new, empty one: never apply such a plan without a restore plan.
Engine major versions: see the
[how-to](docs/how-to/upgrade-the-engine-major-version.md).

## Versioning and releases

Semantic versions, tags `vMAJOR.MINOR.PATCH`, created by release-please from
Conventional Commit pull-request titles. Patch: a fix that changes no plan. Minor: a
new optional input, output or off-by-default resource. Major: anything that can
change or replace an existing caller's resources, or raise a minimum version.
For the contribution and release checks, see [`CONTRIBUTING.md`](CONTRIBUTING.md)
and [the release workflow](.github/workflows/release-please.yml).
